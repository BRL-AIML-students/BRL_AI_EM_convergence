1. 이 프로그램이 하는 일

형상과 크기 조건을 받아 1차 삼각형 표면 메쉬를 만들고, 현재 메쉬의 필수 검사와 독립 파일 검증을 통과하면 NAS 한 건을 발행한다. Solid를 입력해도 내부 tetrahedron을 생성하는 프로그램은 아니다.

이 guide는 함수 구현을 따라가는 코드 해설 대신 입력 → 크기장 → 삼각분할 → 검사 → 개선 → 발행의 판단 흐름을 설명한다. 변수의 기본값은 실제 schema와 실행 코드를 기준으로 적었으며, 예시 숫자와 구분한다.

기준 버전 Gmsh 4.15.2 · Python 3.12.14 · NumPy 1.26.4 · pyNastran 1.4.1. 확인일 2026-10-21. ONELAB의 작업 중 응답과 검사 성능을 개선했다. 품질·기하 검사 기준과 NAS 좌표 정밀도는 유지한다.
용어의미
CAD entity / tagCAD의 point(0D), curve(1D), surface(2D), solid volume(3D)와 그 식별 번호.
node / element / connectivity절점 좌표 / 삼각형 요소 / 각 삼각형을 구성하는 node ID 세 개의 순서. 순서는 법선에도 영향을 준다.
크기장 h(x)공간 위치 x에서 원하는 요소 길이. 실제 생성된 모든 edge의 길이를 정확히 지정하는 표가 아니다.
PIDNAS 삼각형의 구역 ID. 현재는 CAD surface tag와 같다. 재질 또는 EM 물성 번호를 자동으로 부여하는 기능이 아니다.
검사 통과 / 발행검사 통과는 메모리 안의 메쉬 판정이고, 발행은 독립 NAS 검증 후 파일을 확정하는 단계다.
기하 검증 / EM 검증이 생성기는 전자를 수행한다. MoM/RCS 등의 해석 정확도·수렴은 해석기와 기준해를 사용해 별도로 검증해야 한다.

생성 성공 시 오른쪽 창에 삼각형 edge와 face를 표시하고 전체 형상에 화면을 맞춘다. Idle에서는 시점을 바꾸지 않는다. 실패 메시지의 “이번 실행 NAS 없음”과 이전 결과 파일을 구분한다. 형상을 바꿔도 Curvature의 활성 상태와 허용값은 유지한다. 곡면의 편차 검증이 필요하면 직접 켜고 허용값을 정한다. 제공 예제에 명시된 곡률 조건은 그대로 적용된다.

2. 가장 짧은 사용 순서와 Action

새 모듈 폴더에서 설치 후 예제 설정으로 시작한다. GitHub 저장소에서는 이 폴더가 02_BRL_mesh_generator/이다.

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\setup.ps1 -Dev
.\run_gmsh_ui.bat examples\plate.json

창의 ONELAB BRL/00 Action에서 Generate + publish NAS를 선택한다. 완료 여부는 BRL/01 Status, 경로는 BRL/02 NAS path에서 확인한다. CLI는 .\run_cli.bat examples\plate.json으로 같은 코어를 실행한다.

번호 / 실제 UI 선택실제 동작
0 · Idle대기한다. Gmsh Run을 누르는 것만으로 메쉬 생성이나 NAS 발행을 반복하지 않는다.
1 · Generate + publish NAS새 형상·크기장·메쉬를 만들고 검사와 필요한 개선을 거쳐 NAS까지 발행한다.
2 · Generate mesh생성·검사·필요한 개선까지 수행하고 NAS는 쓰지 않는다. 단순한 “삼각형만 생성” 단계가 아니다.
3 · Improve current mesh현재 메쉬를 재검사하고 형상 불량이 있을 때만 제한된 개선을 시도한다. NAS는 쓰지 않는다.
4 · Publish current mesh현재 메쉬를 새로 검사하고 독립 NAS 검증 후 발행한다. 이 Action 자체는 개선을 실행하지 않는다.
5 · Closenative Gmsh 창과 이 실행 session을 종료한다.

Action은 한 번 소비한 뒤 Idle로 돌아간다. Idle에서도 창 조작과 입력은 계속 처리되며, 표시 조건이나 상태가 바뀔 때만 설정창을 갱신한다. 창에 삼각형이 보이는 것과 NAS가 발행된 것은 별개다. Gmsh의 일반 File/Export는 BRL 검사 경로를 호출하지 않으므로, 검증된 NAS는 위 Action 또는 CLI로 얻는다.

생성·현재 메쉬 개선·NAS 검증은 별도 프로세스에서 실행한다. 작업 중에도 창 이동·회전·입력과 Close를 처리한다. Status에 현재 단계가 표시되며, 실행 중 다른 Action을 선택해도 중복 작업을 시작하지 않는다. Close는 진행 중 작업을 취소한다. 작업 중 설정이나 현재 메쉬가 바뀌면 완료된 이전 결과의 발행을 차단한다. 완료 시 CAD import와 화면 표시에는 짧은 시간이 추가로 필요하다.

같은 형상과 Target size라도 파장·국소 크기·Curvature 조건이 다르면 요소 수와 NAS 용량이 달라진다. 특히 작은 곡률 허용값은 목표 길이보다 짧은 edge를 요구한다. 상대 허용오차 0.001을 모든 곡면에 자동 적용하지 않는다. NAS의 좌표는 계속 17자리 유효숫자를 사용해 정확한 round-trip을 보존한다.

ONELAB 시작 시 Wavelength enabled는 기본 ON이다. 시작 JSON에 wave 조건이 없으면 1 GHz·파장당 요소 수 10·상대 유전율 1·상대 투자율 1을 사용하고, 명시된 wave 조건이 있으면 그 값을 유지한다. 실행 중 체크를 해제하면 파장 조건을 끌 수 있다. Target size도 켜져 있으면 두 길이 중 작은 값이 적용된다. CLI/JSON에서 wave를 생략한 의미는 기존처럼 OFF다.

비활성 기능의 입력 후보는 적용 조건이 아니다. 예를 들어 Curvature가 꺼졌을 때의 0.01은 표시용 시작 값이다. 활성 flag와 BRL/03 Applied global size를 함께 확인한다. 고급 entity 선택·수동 영역은 시작 JSON에 지정한다.

현재 구현 근거: native_ui.py, __main__.py, engine.py.

3. 생성부터 발행까지의 전체 흐름

  1. 설정 확인JSON 또는 ONELAB → 같은 schema 검사. 키·단위·경로·수치의 유효성을 확인한다.
  2. CAD 구성native plate/ogive/sphere/cube/cylinder/dihedral 생성 또는 파일 import → 출력 단위로 통일 → surface/PID·예상 경계·기준 방향 확정.
  3. 크기장 구성전역 길이 + 활성화한 특징별 국소 길이 → background field. 곡률 ON이면 국소 callback 추가.
  4. 1D → 2D 메쉬 생성CAD 경계를 분할한 뒤 표면 삼각형을 채운다. 기본 요청은 Algorithm 6.
  5. 곡률 편차 feedback곡률 ON이면 실제 메쉬의 CAD 표본 편차 확인. 초과 entity의 곡률 길이를 보정하고 재생성.
  6. 검사와 필요한 개선구조·topology·방향·기하·ICN·AR/각 검사. 형상만 불량이면 제한된 node relocation → 수용 또는 정확한 rollback.
  7. 현재 메쉬 최종 검사과거 성공 상태가 아니라 지금의 CAD·설정·field·node·connectivity·PID를 다시 확인.
  8. NAS 임시 쓰기 → 독립 읽기 → 확정좌표·ID·연결·PID가 같을 때 고유 run 폴더로 rename. 실패하면 이번 임시 결과만 정리.
필수 검사 오류·미완료·미지원·크기 조건 충돌은 정상 발행으로 바꾸지 않는다. 재생성/개선으로 해결하지 못하면 NAS를 차단한다. 이전 정상 NAS는 덮어쓰지 않는다.

현재 구현 근거: engine.py, inspection.py, improvement.py, nas.py.

4. 입력 형상·단위·경계 의도

기본 길이 단위는 입력과 출력 모두 mm이며 m / cm / mm / um을 지원한다. 크기와 허용 편차를 비교하는 내부 계산은 출력 단위로 통일한다.

설정 JSON은 schema_version=1, geometry, mesh가 필수다. 알 수 없는 키·중복 JSON 키·잘못된 중첩 값은 거부한다. 자동 선택은 해당 선택 키를 생략하거나 UI의 활성 flag로 표현하며, 과거 입력의 별칭을 자동으로 해석하지 않는다.

입력 / 설정현재 처리와 주의점
plateXY 평면의 직사각형. length·width는 양수, origin은 기본 [0,0,0]. 기준 방향은 +Z.
ogiveD=diameter, L=length, t=thickness, origin. D>0, L>D/2, 0≤t<D/2. 기본 t=0. D/L/t 별칭은 받지 않는다.
ogive 생성 원리정확한 원호를 180° 회전하고 복사·180° 회전한다. t=0은 공유 경계를 갖는 두 열린 sheet, t>0은 동심 내측 원호를 사용해 fuse한 벽 두께 solid. STEP 중간 파일은 만들지 않는다.
sphere / cube / cylinder구·정육면체·끝면을 포함한 원기둥 solid. radius / side / radius·height는 양수. origin 의미와 축은 아래 그림을 따른다.
dihedral공통 +Z 모서리를 공유하는 두 sheet. length·width1·width2>0, 0<angle_deg<180. 기본 각도 90°. 기준 법선은 열린 쐐기 안쪽이다.
STEP/STP·IGES/IGS파일에 들어 있는 길이 단위를 output_unit으로 변환한다. length_unit을 다시 곱하지 않는다. 확장자의 대소문자는 구분하지 않는다.
BREP자체 단위가 명확히 저장되는 STEP과 달리 length_unit을 입력 단위로 사용한다. 전체 compound를 한 번 변환해 독립 sheet·curve·point도 CAD에 보존한다.
mesh.target_size, minimum_size, 수동 size/bounds/거리, absolute_tolerance, protected_gap모두 output_unit 기준. native 형상 치수와 origin은 length_unit 기준.
상대 CAD path / output_dir설정 JSON 파일이 있는 폴더 기준. output_dir 생략 시 그 위치의 outputs. 제공 예제는 자체 output_dir 설정을 확인한다.
PID / Physical GroupCAD surface tag와 PID를 대응시킨다. CAD revision이나 Gmsh build가 바뀌면 tag가 같다는 보장은 없다.
CAD sheet 방향sheet_normal=+1/-1 또는 sheet_normals의 면별 값으로 CAD parameter normal의 기준 방향을 지정한다. 면별 값 우선. 열린 sheet에 solid의 “바깥”을 자동 가정하지 않는다.
solid 방향면 법선의 양쪽 점이 solid 안/밖인지 CAD로 확인해 outward와 비교한다. native ogive t=0은 해석적 외측 기준을 갖는다.

4.1 형상 정의와 파라미터 그림

UI의 BRL/10 Geometry에서 7가지 입력을 선택한다. 아래 geometry 예시는 전체 JSON의 해당 부분이며, 실행 가능한 전체 설정은 examples/에 있다. Native 치수와 origin=[x,y,z]는 length_unit 기준이다. 그림의 예제 숫자는 mm를 가정한다. 그림은 형상 정의를 위한 개념도로, 메쉬나 정확도 보증을 뜻하지 않는다.

모든 native 형상의 origin 기본값은 [0,0,0]이다. origin만 바꾸면 형상 전체가 같은 벡터만큼 이동한다. 크기·각도는 바뀌지 않는다. 치수는 JSON에 명시해야 하며 표의 “UI 시작 값”은 다른 형상으로 전환할 때 제공하는 입력 후보다. 선택한 형상의 파라미터만 보이고, 생성 후 값을 바꾸면 다시 Generate해야 한다.

plate ogive sphere cube cylinder dihedral cad

plate · 평판

XY 평면에 놓인 두께 없는 직사각형 sheet다. O=origin은 최소 X·Y 모서리이며, length는 +X, width는 +Y 방향이다. 모든 면 법선은 +Z를 기준으로 한다.

파라미터정의·UI 시작 값·효과
length양수. UI 시작 값 100. +X 길이만 바뀐다.
width양수. UI 시작 값 60. +Y 폭만 바뀐다.

예를 들어 length만 2→3으로 바꾸면 +X 방향으로만 1만큼 늘어난다.

{"kind":"plate","length":2,"width":1,"origin":[0,0,0]}

ogive · 접선형 회전체

O는 바닥 원의 중심이고 축은 +Z다. 바닥 외경 D, 외부 tip 높이 L의 원호 단면을 회전한다. t=0은 바닥이 열린 sheet이며, t>0은 내측 원호와 바닥 고리로 닫힌 벽 두께 solid다.

파라미터정의·UI 시작 값·효과
diameterD>0. UI 시작 값 2. 바닥 외경이며 반경이 아니다.
lengthL>D/2. UI 시작 값 3. 바닥에서 외부 tip까지의 높이.
thickness0≤t<D/2. UI 시작 값 0. 같은 원호 중심에서 내측 원호 반경을 t만큼 줄인다. +Z 방향 일정 두께가 아니다.

D를 늘리면 같은 L에서도 더 넓은 원호 형상이 된다. t를 늘리면 내부 공간이 줄어들지만 외부 형상은 유지된다. 예제: ogive.json, ogive_wall.json.

{"kind":"ogive","diameter":2,"length":3,"thickness":0.2}

sphere · 구

O=origin을 중심으로 하는 완전한 구 solid다. 반지름은 세 축에 동일하게 적용하며 방향 파라미터는 없다. NAS에는 구의 바깥 표면만 발행한다.

파라미터정의·UI 시작 값·효과
radiusr>0. UI 시작 값 1. 각 축의 범위는 중심 좌표에서 −r부터 +r까지다.

origin=[10,20,30], radius=1이면 X=9…11, Y=19…21, Z=29…31이다. 예제: sphere.json.

{"kind":"sphere","radius":1,"origin":[0,0,0]}

cube · 정육면체

O=origin은 X·Y·Z가 모두 최소인 모서리다. +X·+Y·+Z 방향으로 같은 길이만큼 뻗는 닫힌 solid다. 직육면체의 세 길이를 따로 받는 형상이 아니다.

파라미터정의·UI 시작 값·효과
sidea>0. UI 시작 값 2. 세 축 모두 origin 좌표부터 origin+a까지다.

origin=[10,20,30], side=2이면 X=10…12, Y=20…22, Z=30…32다. 예제: cube.json.

{"kind":"cube","side":2,"origin":[0,0,0]}

cylinder · 양 끝이 막힌 원기둥

O=origin은 바닥 원의 중심이다. 중심축은 +Z이고 높이는 바닥에서 위쪽으로 잰다. 원통 측면과 두 원형 끝면을 포함한 닫힌 solid다.

dihedral · 공통 모서리를 갖는 두 평판

두께 없는 직사각형 sheet 두 장이 O에서 +Z로 뻗는 모서리를 공유한다. 첫 판은 +X 방향, 둘째 판은 XY 평면에서 +X를 기준으로 +Z 쪽에서 보아 반시계 방향으로 θ만큼 회전한다. 두 판 사이의 열린 쐐기 영역을 향하도록 법선을 정한다.

파라미터정의·UI 시작 값·효과

width1w1>0. UI 시작 값 2. 첫 판이 공통 모서리에서 +X로 뻗는 폭.
width2w2>0. UI 시작 값 2. 둘째 판이 회전된 방향으로 뻗는 폭.

L은 두 판을 함께 길게 하고, w1·w2는 해당 판만 넓힌다. θ만 바꾸면 폭과 길이는 유지되고 벌어짐만 달라진다. 공통 모서리의 node를 공유하므로 두 판을 서로 떨어뜨린 CAD가 아니다. 예제: dihedral.json.

{"kind":"dihedral","length":2,"width1":2,"width2":1.5,"angle_deg":90}

Dihedral의 두 판은 다음과 같이 정의된다. O=origin, 첫 판은 0≤u≤w1, 둘째 판은 0≤u≤w2이며 두 판 모두 0≤v≤L이다. θ는 angle_deg를 radian으로 변환한 값이다.

Dihedral 기준 법선은 첫 판 +Y, 둘째 판 (sin θ, −cos θ, 0)이다. 닫힌 solid가 아니므로 별도의 바깥쪽 체적을 가정하지 않는다. Sphere·cube·cylinder는 CAD solid로 구성하지만 제품은 그 경계의 1차 삼각형만 생성하며 체적 요소는 만들지 않는다.

5. 전역 크기: cap·파장·fallback

먼저 모든 국소 규칙의 바깥 기준이 될 전역 요청 길이 hg를 구한다. 사용자 cap과 파장 조건이 둘 다 있으면 더 작은 길이를 쓰고, 둘 다 없을 때만 bbox fallback을 쓴다.

6. 국소 크기: 작은 특징을 각자 측정한다

국소 규칙은 모두 기본 OFF다. 켜진 규칙만 CAD를 측정하며, 특징마다 독립적으로 목표 길이 hf를 만든다. h_f가 h_g보다 작을 때만 세분화 field를 추가한다. 하나의 아주 작은 edge 때문에 모든 다른 특징의 목표를 일괄 교체하지 않는다.

규칙 / JSON 키 (mesh.local 아래)측정·초기 목표예와 지원 범위
short_edges실제 CAD curve의 arc length / divisions기본 divisions=3. 길이 0.6 mm curve이면 0.2 mm. 기본 선택은 surface 경계의 non-seam curve이며 null pole은 유한 짧은 edge로 취급하지 않는다.

short_edges/widths.entities를 비우면 해당 규칙의 기본 전체 대상, 지정하면 그 tag만 선택한다. gaps.pairs는 실제 surface tag 쌍 목록이며 비우면 독립 성분의 후보 쌍을 찾는다. 곡면·구멍·비볼록 neck을 포함한 CAD 전체에 widths를 켜면 미지원으로 차단될 수 있다. 이 경우 지원하는 면만 지정하거나 수동 curve/box·곡률 제어를 사용한다.

Gap은 최소 거리와 가까운 연결 구간을 감싸는 보수적인 축 정렬 Box에 적용한다. 일반 곡면 전체에 “어디서나 일정한 gap”을 측정한 지도는 아니며, 빈 공간에 volume 요소를 몇 층 넣는 기능도 아니다. 분리 entity의 접촉/모호한 0 gap을 자동 node 병합으로 해결하지 않는다.

geometry.separated_surfaces와 geometry.protected_gap은 분리 의도·topology tolerance 판단을 위한 설정이다. 이 값을 넣는 것만으로 gap 크기장이 켜지지 않는다. 실제 측정·세분화는 mesh.local.gaps.enabled=true가 필요하다.

변수 (mesh.local)기본값 / 자동 적용바꿀 때의 효과
hold_distance생략하면 해당 특징의 h_f작은 길이를 그대로 유지할 거리. 늘리면 촘촘한 영역이 넓어진다. 0도 허용.

8.1 초기 목표

curve는 실제 곡률, surface는 두 주곡률의 절댓값 중 큰 값을 사용한다. R=1/κ로 해석할 수 있는 보통의 원호에서 초기 edge 길이는 sagitta 관계를, surface에서는 삼각형 내부 편차의 근사식을 쓴다. 둘 다 h_g를 넘지 않게 한다.

hcurve=22Rδ−δ2,hsurface≈6Rδ

평면 κ=0은 전역 cap을 유지한다. δκ≥1인 매우 작은 반경에는 유한 편차 해상도 min(h_g,δ)를 사용한다. 극점에서 미정 곡률이 나오면 유효한 인접 parameter 위치에서 다시 구하고, 여전히 유효하지 않으면 차단한다. 초기 추정값 자체를 최대 편차의 증명으로 취급하지 않는다.

R=10 mm, δ=.001 mm인 원의 균등 chord 요구는 223분할이다. 이 코드에는 고정 200 clamp가 없다. 이 “필요 분할”은 곡률 요구의 해석이며, 임의 곡선의 최종 edge 개수를 사용자가 정확히 지정하는 기능은 아니다.

8.2 생성 후 편차와 재생성

각 triangle 내부·edge와 CAD 경계 line을 표본화해 mesh → CAD 거리를 구한다. 원본 element ID·entity 대응, 좌표/parameter round-trip, trim 영역 포함을 확인한다. 구멍을 가로지르는 chord처럼 underlying surface 투영점이 실제 face 밖이면 그 face의 유효 경계 curve 후보로 거리를 다시 확인한다.

각 entity의 최대 표본 거리/δ를 q로 두고 q≤1이면 해당 표본 조건을 충족한다. q>1이면 해당 entity의 보정 배율에 0.7/√q를 곱한다. 적용 길이는 δ+(초기 길이−δ)×배율이다. 끝점에서 초기 길이가 δ이면 재분할로 이를 더 줄이지 않는다. 실제 편차 검사는 유지하며 최소 크기를 기준으로 요청을 clamp하지 않는다. 원래 CAD에서 메쉬 전체를 새로 생성한다.

재생성은 connectivity·node/element ID를 바꿀 수 있다. 뒤에서 설명하는 연결을 보존하는 node relocation과 구분한다. 최종 편차 초과·투영 실패·최소 길이 충돌·재생성 횟수 소진은 발행 차단이다.

이 편차는 유한 표본이며 연속 최대 거리나 양방향 Hausdorff 거리가 아니다. Trim 경계 보정은 평면에서 최근접 거리를 주지만 일반 곡면에서는 검증된 유효 CAD 점까지의 보수적인 거리다. DiscretizationError Plugin은 이 원본 ID·투영 성공 계약 때문에 현재 경로에 채택하지 않았다.

12. 개선 후보의 수용과 정확한 rollback

improvement.enabled=true, max_passes=3이 기본이며 횟수는 0 이상 정수다. enabled=false 또는 횟수 0은 이동을 생략할 뿐 발행 검사를 끄지 않는다. 정상 shape는 불필요하게 옮기지 않으며 topology·법선·필수 측정 문제가 있으면 이 개선 루프에 들어가지 않는다.

  1. node 좌표·CAD parameter·분류, 모든 요소 연결, ID·PID·entity/Physical Group, 고정 경계의 복구 기준을 확보한다.
  2. 1회씩 Relocate2D → Laplace2D → Relocate2D …를 번갈아 적용한다. 전자는 node 재배치, 후자는 이웃 관계를 이용한 Laplace smoothing이다. 세부 구현을 BRL이 다시 만드는 것이 아니라 Gmsh API를 호출한다.
  3. 현재 후보를 처음부터 다시 검사한다. 연결·ID·분류·PID·entity가 같고 point/curve node와 parameter가 그대로여야 한다.
  4. 최악 AR·최소각·최소 ICN이 악화되지 않아야 하며, 형상 위반 개수가 줄거나 같은 개수에서 최소 ICN이 상승해야 한다. 실제 크기 비율·인접 크기 비율·CAD node/centroid 편차·면적/체적 상대 오차·활성 표본 편차도 비악화를 요구한다.
  5. 후보를 거부하면 저장한 node 좌표와 parameter를 정확히 복구하고 재검사한다. 연결까지 바뀌어 좌표 복구로 원상태가 되지 않으면 발행을 차단한다.

중간 후보의 형상 위반이 감소해도 아직 남을 수 있다. 제한된 횟수 뒤 최종 AR·각 조건을 만족하지 못하면 NAS는 발행하지 않는다. 예외로 끝난 개선을 “복구했으니 성공”으로 처리하지 않는다.

Node relocation으로 T-junction·누락 연결·CAD 구멍을 수리했다고 보지 않는다. 곡률 feedback의 재생성은 연결 변경을 허용하지만, 여기의 개선은 기존 연결 보존을 요구한다.

13. 발행 성공을 확인하는 방법

최종 발행은 현재 상태 검사 → 임시 쓰기 → 자체 strict parser → 독립 pyNastran 읽기 → 확정 순서다. NAS에는 GRID(node), CTRIA3(triangle/PID), ENDDATA와 간단한 단위 주석을 쓴다. 이것이 재질·하중·해석 제어 카드까지 갖춘 Nastran 해석 deck이라는 뜻은 아니다.

독립 읽기는 단순히 파일이 열리는지만 확인하지 않는다. node/element ID 집합, 각 좌표, 삼각형의 node 순서, PID가 현재 메쉬와 정확히 일치하는지 대조한다. 임시 파일은 output_dir 아래 .pending-…에 쓰고 검증 뒤 같은 파일시스템의 run_<형상·치수·고유 ID>/mesh.nas로 확정한다. 실패하면 이번 pending만 정리하고 이전 run은 보존한다.

관측한 상태해석
UI: NAS published + BRL/02 NAS path이번 발행 경로가 완료되어 해당 NAS 위치를 제공했다.
UI: Mesh ready: required checks passedGenerate mesh가 완료된 상태다. 아직 새 NAS를 발행한 것은 아니다.
UI: Blocked: … / Regenerate required: …실패 이유를 확인한다. 화면의 메쉬나 예전 run 파일이 있어도 이번 조건의 성공으로 판단하지 않는다.
CLI exit 0 / status=ok / nas_path성공. stdout의 경로로 NAS를 확인한다.
CLI exit 2 / status=blocked / reason필수 검사·미완료 등의 이유로 발행 차단. 상태 JSON은 stderr에 나온다.
CLI exit 1 / status=error / reason입력 또는 실행 오류. 상태 JSON은 stderr에 나온다.

정상 run 폴더에는 mesh.nas 한 건만 있다. 제품에 score·등급·보고서·diagnostic.msh·별도 log 파일을 만들지 않는다. 본 guide와 개발 테스트 기록은 개발 문서이며 제품의 결과 보고서와 구분한다.

현재 구현 근거: engine.py, nas.py, __main__.py, native_ui.py.

15. 폴더와 .git: 한 곳에 모을 수 있는가

프로젝트 전체를 하나의 바깥 폴더에 두는 것은 가능하고 일반적이다. 다만 그 안의 .git, Python 환경, 소스, 설정 파일은 서로 다른 역할을 갖는다. 모두 임의의 “기타” 하위 폴더로 옮기는 방식은 현재 실행 경로와 Git의 저장소 인식을 바꾸므로 그대로 적용할 수 없다.

항목역할정리할 때의 판단
.git/commit·branch·원격 연결·index 등을 관리하는 Git 데이터베이스. 프로그램 실행 코드나 Python 패키지가 아니다.일반 checkout의 저장소 루트에 둔다. 삭제하면 그 사본의 로컬 이력/branch 관리를 잃는다. 다른 보조 파일과 함께 임의 이동하지 않는다.
.gitignore / .gitattributesGit 추적 제외 규칙 / 줄바꿈·텍스트 처리 규칙. .git와 다른 작은 설정 파일.무시 대상을 정의하고 줄바꿈을 재현하는 데 필요하다. root 기준 경로가 있으므로 그대로 유지하는 편이 단순하다.
.venv/이 프로젝트의 Python 실행 환경과 설치 패키지.setup으로 재생성할 수 있다. 환경 안에 경로 의존성이 있어 폴더 이동/프로젝트 이름 변경 뒤에는 재생성이 원칙이다.
.tools/setup이 설치한 uv·관리 Python 등 실제 도구.다른 위치로 둘 수 있지만 setup과 Python/환경 참조를 함께 바꿔야 한다.
.cache/다운로드·uv·테스트 등 중간 작업 데이터.보통 재생성 가능하지만 현재 프로젝트에는 전달용 Git checkout도 들어 있다. 지금은 폴더 전체를 일반 임시 캐시처럼 삭제하면 안 된다.
brl_mesh/실제 import되는 Python package.패키지 이름이며 프로젝트 바깥 폴더 이름과 별개다. brl_mesh_generator라는 바깥 폴더를 쓴다고 package까지 같은 이름으로 바꿀 필요는 없다.
tools/ (점 없음)개발자가 작성한 작은 smoke/probe 도구 코드.설치된 binary를 두는 .tools/와 다르다. Git에 보존하는 개발 코드다.
pyproject.toml / uv.lock / .python-version프로젝트 의존성·정확한 버전 잠금·Python 버전 선택.모듈 루트에서 setup이 읽는다. 한 보조 폴더로 옮기면 관련 경로/실행 방식을 함께 변경해야 한다.
docs / examples / tests / outputs사용/검증 문서 / 입력 예제 / 개발 검증 / 발행 결과.앞의 세 폴더는 source와 함께 관리한다. outputs는 사용자 결과이며 캐시 정리 대상으로 자동 삭제하지 않는다.

16.1 현재 PC에 .git가 두 군데 보일 수 있는 이유

Codex/02_BRL_mesh_generator/        ← 독립 재작성 source
├─ .git/                           ← 원본 단계별 개발 이력
├─ brl_mesh/ · docs/ · examples/
├─ .venv/ · .tools/ · outputs/
└─ .cache/github-delivery/          ← GitHub 전달용 별도 checkout
   ├─ .git/                        ← 기존 GitHub main에 연결한 이력
   └─ 02_BRL_mesh_generator/        ← 저장소 안의 새 모듈
      ├─ brl_mesh/ · docs/ · examples/
      └─ …

이 이중 사본은 독립 재작성 이력을 유지하면서 기존 저장소에 교체 PR을 만들기 위해 사용한 작업 방식이다. 메쉬 생성기가 실행되기 위해 두 저장소가 필수인 것은 아니다. GitHub에서 일반적으로 새로 clone하면 저장소 루트의 .git 하나가 여러 모듈을 관리하고, 02_BRL_mesh_generator 안에 추가 .git를 만들 필요가 없다.

16.2 장기적으로 단순하게 쓰는 구성

brl_mesh_generator/                ← PC의 clone 폴더명은 선택 가능
├─ .git/                           ← GitHub 저장소 전체를 관리
├─ README.md · AGENTS.md · setup.*
└─ 02_BRL_mesh_generator/           ← 현재 GitHub 배치를 유지
   ├─ brl_mesh/ · docs/ · tests/ · examples/
   ├─ pyproject.toml · uv.lock · setup.ps1
   ├─ .venv/ · .tools/ · .cache/
   └─ outputs/

GitHub 저장소명과 PC의 바깥 clone 폴더명은 달라도 된다. “한 폴더에서 관리”가 목적이면 이런 하나의 공식 checkout으로 작업하는 방식이 단순하다. 지금의 별도 source/전달 사본을 실제로 통합하려면 미게시 로컬 commit과 사용자 결과를 먼저 보존하고 환경을 다시 구성해야 한다. 이번 문서 작업에서는 이동·통합·삭제를 수행하지 않았다.

환경 파일만 덜 보이게 하고 싶으면 향후 .runtime/ 아래에 venv·도구·진짜 cache를 모으도록 설계할 수 있다. 이 경우 setup·launcher·VS Code·ignore 경로와 테스트를 함께 고쳐야 하며, .git와 프로젝트 설정까지 모두 그 폴더로 밀어 넣는 것과는 다르다. Git 메타데이터를 외부에 두는 고급 구성도 있지만 연결용 .git 파일과 경로 관리가 필요해 초보 사용자의 단순화 목적에는 이점이 적다.

근거: 현재 setup.ps1·launcher·Git root를 직접 확인했다. 일반 구조는 Git repository layout, 환경 이동은 Python 3.12 venv의 non-portable 환경 설명을 참고했다.
